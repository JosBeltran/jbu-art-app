# Fine Art Prints commerce integration

Product Studio and Wall Art Studio write independent product drafts, candidate mappings, preview recipes and draft prices. Product Manager reviews those records. The storefront currently reads legacy `artwork_prints` in `publicPrintDiscovery.server.js`; `/prints/[variantId]` resolves both artwork SKUs and historical variant URLs. `CartContext` persists legacy prints separately from original artwork rows and selects the appropriate existing Stripe Checkout path. Verified payment webhooks create orders transactionally, including original ownership and limited-edition reservations. None of those inventory or certificate paths should be used for an independent made-to-order reproduction.

The bridge uses the existing artwork page, destination selection, cart and Stripe endpoints. Publication and an approved commercial gallery precede public discovery. Checkout resolves the approved country/currency price on the server, pins the configuration and amount in a durable manifest and writes an independent immutable order-line snapshot after verified payment. Wall Art Studio preview recipes remain visibly separate from rendered gallery images. Supplier-submitted orders remain outside this release.

## Staging and acceptance

1. Apply `20261213_fine_art_commerce.sql` after the Wall Art Studio migration.
2. Create or open a Product Studio draft linked to an artwork already enabled for prints. Enter both descriptions, configure dimensions and destination countries, and validate a production derivative and supplier mapping where needed.
3. Use the variant's **Verified commercial gallery** to upload a reviewed JPG, PNG or WebP. The gallery records the source (studio, JBU or supplier), bilingual alt text, primary status and the variant configuration that was reviewed. Use renders only after confirming the actual substrate, finish, crop and dimensions. Approximate Wall Art Studio scenes are still preview recipes. Provider mocks may be imported only as verified, authorized uploads. Provider asset generation is outside this change.
4. Approve at least one exact destination/charge-currency price and activate its price book. The existing Stripe and order accounting system settles in MXN or USD. Other currency books can remain in the planning catalogue until those currencies have a supported settlement path. Review requirements and publish individual variants. Unpublishing immediately hides the current offer while preserving previously frozen sessions.
5. Open the linked artwork under `/prints`, change formats and verify image, specifications and approved price. Add a variant to the existing cart and change its quantity. The cart keeps country and currency attached to each added presentation. Mixed carts allow selecting the group to pay so legacy workflows retain their own checkout terms.
6. Use a Stripe test-mode deployment and confirm a paid test Checkout Session with the registered webhook. Verify the corresponding order contains `catalog_configuration_snapshot`, including the artwork/product/variant association, exact approved entry, amount, currency, destination and selected attributes. The independent path uses made-to-order capacity and creates no supplier job, artwork ownership or limited edition certificate. Supplier preparation for newly independent paid lines requires a later integration or manual handling.

The purchase path revalidates the price and destination, bypasses legacy welcome discounts for exact price-book settlement, and freezes item and shipping manifests before returning a Checkout URL. Only the verified paid webhook creates orders. Stripe retries use the same database order. Catalog-only checkout requires an authenticated collector. Existing legacy public routes, original sales and their metadata are retained. An optional Open Edition replacement hides the old option in the configurator when the replacement has an eligible price in the selected market; direct legacy URLs still resolve.

Rollback application deployment before removing the migration. Unpublish independent variants first and keep the new checkout and order snapshot records for open Stripe Sessions and historical receipts. Never drop or rewrite paid order snapshots during a rollback.
